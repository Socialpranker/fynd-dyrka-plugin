<a id="когда"></a>
## 1. Когда фан-аут оправдан, а когда вреден

**Оправдан:** репо, где инвентарь Шага 2 дал больше ~100 точек входа, или
кодовая база физически не читается одним контекстом (десятки тысяч строк в
релевантных модулях).

> **Что фан-аут даёт на практике** (замер 05.08.2026, FYND_DYRKA). Два
> предыдущих полных аудита одним агентом пропустили две вещи, которые узкие
> линзы нашли сразу:
> - `exposure` → **fail-open в rate-limit**: `catch` возвращает
>   `{allowed:true}`, при недоступности Redis лимиты молча снимаются со всех
>   эндпоинтов сразу;
> - `state-money` → **двойное списание в `captureHold`**, воспроизведено на
>   реальном Postgres (баланс 20 → −20 при двух параллельных вызовах).
>
> Общий агент оба места **читал** и счёл нормальными. Узкая линза дошла до
> обработки ошибок и до границ транзакции, потому что больше ей смотреть было
> некуда. В этом вся ценность: не в объёме, а в глубине одного вопроса.

**Два режима, и выбор между ними важнее размера флота:** разбиение по
инвентарю (волны 1–2 ниже) — когда инвентарю Шага 2 можно доверять; **рой по
открытой территории** (раздел 4а) — когда нельзя, потому что репо незнакомый
или инвентарь мог пропустить целый класс входов. Замер: на репо, где половина
поверхности лежала вне HTTP-роутов, первый режим дал 1 находку из 5, второй —
5 из 5.

**Вреден** — и это чаще, чем кажется:

- **Маленький/средний репо.** Один агент, читающий весь auth-путь целиком,
  видит цепочку «эндпоинт → middleware → проверка прав → запрос в БД». Пять
  агентов, читающих по куску, эту цепочку не видят ни один. Фан-аут покупает
  объём ценой связности — не плати эту цену без нужды.
- **Когда нужна одна конкретная проверка.** «Посмотри, нет ли SSRF в воркере» —
  это работа на один контекст, а не на флот.
- **Когда у тебя нет инвентаря — но только для разбиения по линзам.** Волны 1-2
  без Шага 2 это пять агентов, каждый из которых заново гадает, что смотреть:
  инвентарь и есть их план разбиения. К режиму роя (раздел 4а) это НЕ относится
  — он специально работает без инвентаря и выдаёт агентам территорию, а не срез.
  Нет инвентаря и нет времени его строить → рой, а не волны.

> Субагент стартует с **чистым контекстом**: не видит историю разговора, твой
> инвентарь, уже прочитанные файлы. Всё, что ему нужно знать, должно быть в
> его промпте. Это главный источник провальных фан-аутов — агент получает
> «проверь auth» без указания, где auth, и тратит половину бюджета на поиск.

<a id="архитектура"></a>
## 2. Архитектура: две волны + верификация

```
Шаг 2 (инвентарь)
      │
      ├──── Волна 1: N агентов-искателей, по линзам ────┐
      │     каждый: своя линза × свой срез кода         │
      │     выход: кандидаты (гипотезы, НЕ находки)     │
      │                                                  ▼
      │                                        дедуп кандидатов
      │                                        (плоским кодом, не агентом)
      │                                                  │
      ├──── Волна 2: цепочки между линзами ──────────────┤
      │     вход: сводка кандидатов волны 1              │
      │     ищет: связки, которых не видит одна линза    │
      │                                                  ▼
      └──── Верификация: по одному агенту на кандидата ──┘
            вход: ТОЛЬКО заявление, без reasoning автора
            задача: опровергнуть, а не подтвердить
            выход: подтверждено / снято / не проверяется
                            │
                            ▼
                   Шаг 5 (сканеры) → Шаг 6 (триаж) → отчёт
```

Ключевое: волна 1 выдаёт **кандидатов**, а не находки. Находкой кандидат
становится только после верификации с прогоном.

<a id="волна-1"></a>
## 3. Волна 1 — discovery по линзам

Разбиение **по линзам** (классам уязвимостей), а не только по файлам. Причина:
агент с линзой «IDOR» и агент с линзой «гонки», читая один и тот же файл,
видят разное. Файловое разбиение даёт объём, но каждый агент смотрит «вообще на
всё» и находит то, что бросается в глаза.

Базовый набор линз — по одному агенту на линзу:

| Линза | Что ищет | Куда смотреть (из инвентаря) | Ссылка |
|---|---|---|---|
| `authn` | fail-open, небезопасное сравнение секретов, обход проверки | точки входа + «секреты и доверие» | API2 |
| `authz` | BOLA, BOPLA, BFLA — три разных бага, см. ниже | точки входа + запросы к БД | API1/3/5 |
| `ssrf-inject` | SSRF, SQLi, командная инъекция, traversal, десериализация | «ввод, уходящий вовне» | API7 |
| `state-money` | гонки, двойное списание, TOCTOU, обход шагов процесса | «мутации состояния и денег» | WSTG-BUSL |
| `exposure` | debug/demo/internal-роуты без auth, отсутствие rate-limit | точки входа без auth | API4 |
| `audit` | отсутствие аудит-лога значимых действий (STRIDE «R») | «мутации состояния», админ-действия | STRIDE |

### Линза `authz` — три раздельных вопроса, не один

«Проверь IDOR» — слишком размыто, агент проверит только первый случай. Спрашивай раздельно:

- **BOLA** (доступ к чужому объекту). Эндпоинт берёт `id` из запроса и делает
  `WHERE id = :id` без `AND owner_id = :current_user`? Проверка владения есть,
  но **после** действия, а не до?
- **BOPLA** (доступ к чужим *полям* того же объекта). Два подслучая, оба
  пропускаются чаще всего:
  - *mass assignment*: апдейт биндит весь входящий JSON на модель без allowlist
    полей — клиент шлёт `{"role":"admin"}` или `{"credits":9999}`, и это проходит;
  - *excessive exposure*: ответ сериализует объект целиком без allowlist —
    в JSON утекают хэш пароля, внутренние флаги, чужие поля.
- **BFLA** (доступ к чужой *функции*). Админский эндпоинт проверяет только
  «залогинен», а не «залогинен И роль=admin»? Сверь список ролей, который
  реально проверяется, со списком, которому функция должна быть доступна.

### Линза `state-money` — добавь обход процесса

Кроме гонок проверь **circumvention of workflows**: можно ли пропустить
обязательный шаг многошагового процесса? Оплата → выдача без подтверждения
оплаты; верификация → привилегия без верификации; черновик → публикация мимо
модерации. Признак в коде: переход состояния делается по запросу клиента, а
не выводится из предыдущего состояния на сервере.

Второе: **лимиты на повторное использование** — промокод/инвайт/триал,
который должен срабатывать один раз, но серверной проверки этого нет.

На большом репо линзу дополнительно режут по срезу кода: `authz × src/api/v1`,
`authz × src/api/v2`. Комбинация «линза × срез» — единица работы одного агента.

**Каждому агенту в промпте обязательно дать:**

1. Конкретные пути файлов из инвентаря — не «найди auth», а «читай эти файлы».
   Инвентарь деградировал до уровня модулей (репо больше ~100 точек входа, см.
   SKILL.md «Деградация на большом репо») — тогда путей в нём нет, и агент
   получает **границу зоны**: модуль/сервис плюс требование первым делом самому
   построить поэндпоинтный список внутри неё и вернуть его вместе с находками.
   Чего нельзя — выдать строку модуля молча, как будто это путь: агент потратит
   половину бюджета, выясняя, где вообще начинается его зона.
2. Его линзу и **только её** — расфокусированный агент возвращает мусор.
3. Требование вернуть структурированный список кандидатов с `file:line`.
4. Запрет создавать субагентов (иначе рекурсия и потеря отчёта).
5. Явное «отсутствие находок — валидный ответ» — иначе агент придумает находку,
   чтобы не выглядеть бесполезным. Это реальный режим отказа, не теория.
6. **Разрешение дойти до реализации проверки**, на которую опирается выданный
   срез (см. ниже) — иначе агент оценивает вызов `validate(x)`, не открывая
   `validate`.
7. **Обязательное поле `blind_spots`** — что он должен был прочитать, но не смог.

### Срез — это старт, а не забор

Формулировка «читай ТОЛЬКО эти файлы» экономит контекст, но обрезает ровно ту
поверхность, где чаще всего и лежит баг: проверка вызывается в срезе, а
написана вне его.

> **Замер (baseline этого скилла, 16.08.2026).** Эндпоинт в выданном срезе
> корректно вызывал `validate_redirect()` и `is_internal_host()`; обе функции
> с дырками (`host.endswith(allowed)` пропускает `evilexample.com`; проверка
> внутренних адресов сравнивает строковые префиксы) лежали в соседнем модуле
> вне среза. Два агента из двух **не открыли** его — оба написали «вне
> разрешённой зоны» — и вернули вместо находок шаблонные гипотезы из приоров
> (DNS rebinding, `::ffff:`, decimal IP). Реальные баги не назвал ни один.
>
> Тот же эффект в замере Anthropic на 15 OSS-проектах (13.08.2026): половина
> находок координирующегося роя оказалась **вне** тех директорий, куда были
> направлены независимые агенты; пересечение двух методов — 12 находок из
> 266 и 21. Методы комплементарны: партиционирование ищет там, куда указали,
> самонаведение находит, где искать.

Правило: агент **обязан** прочитать реализацию любой функции из своего среза,
от которой зависит вердикт «безопасно» — по импорту, на любую глубину. Это не
расширение линзы: линза прежняя, меняется только граница чтения. Всё
остальное вне среза он не трогает, а записывает в `blind_spots`.

`blind_spots` — вход волны 2 наравне с кандидатами. Агенты сами называют, где
дыра в покрытии; в baseline оба написали «требует чтения `lib/urlcheck.py`» —
это готовый адрес для следующей волны, и терять его нельзя.

### Не дублируй линзу ради уверенности

Два агента с одной линзой, одним срезом и одной моделью возвращают один
результат — в baseline выше две реплики совпали по составу и порядку
кандидатов. Второй агент на ту же линзу не повышает надёжность, он повышает
счёт. Надёжность даёт верификация (раздел 5), а разнообразие — другая линза,
другой срез или другая модель.

<a id="волна-2"></a>
## 4. Волна 2 — цепочки между линзами

Любое разбиение теряет многошаговые атаки: IDOR без rate-limit — это одна атака,
но линза `authz` видит только первую половину, линза `exposure` — только вторую.

Поэтому после волны 1 запускается **один** агент (не флот), который получает
сводку всех кандидатов и ищет связки:

- утёкший ключ + эндпоинт, который его принимает;
- открытый роут + дорогая операция за ним = ресурсное истощение;
- IDOR + отсутствие лимита = массовая выкачка чужих данных;
- слабая валидация + путь до `subprocess`/SQL.

Вход волны 2 — компактная сводка (заголовок + `file:line` + линза), не полные
отчёты агентов. Иначе контекст переполнится тем же, чего мы избегали.

<a id="рой"></a>
## 4а. Режим «рой» — когда инвентарю нельзя доверять

Волны 1–2 выше распределяют агентов **по инвентарю**: ищут там, куда указали.
Это и есть их потолок — инвентарь, пропустивший зону, делает её невидимой для
всего фан-аута сразу.

Режим роя решает другую задачу: агентам **не выдаётся срез**, выдаётся
территория целиком, и они сами решают, где копать.

**Когда переключаться на рой:** незнакомый репо; подозрение, что инвентарь
неполон; аудит перед сдачей, где цена пропуска выше цены токенов. Когда НЕ
надо: инвентарь надёжен и мал — рой потратит бюджет на переоткрытие известного.

> **Замер 16.08.2026** (Flask-сервис + `ops/` + миграции, 5 посаженных багов).
> Партиционирование по инвентарю HTTP-точек входа — **1 из 5**. Рой из трёх
> агентов по открытой территории — **5 из 5**, плюс цепочка между двумя
> файлами (`restore_archive` распаковывает архив в тот же каталог, откуда
> `load_state` читает pickle → RCE), которую нашли все трое.

### Протокол

Форум — каталог `forum/`, файл на агента (`agent-N.md`), пишет только свой,
читает все. Отдельный файл на агента вместо общего убирает гонку записи.

Формат отчёта агента — он же формат файла форума:

```
ZONE: <что взял>
WHY: <одна строка, почему сюда>
FINDINGS: список "claim | file:line"
MAP: каждый файл территории — осмотрен / не смотрел
NEXT: что стоит взять следующему и почему
```

`MAP` и `NEXT` важнее `FINDINGS`: они превращают личный проход в общую карту.

**Раунды, а не параллельный залп.** В том же замере три агента, стартовавшие
одновременно в пустой форум, все трое написали «форум пуст, я первый» и взяли
**одну и ту же** зону. Координации не было — выигрыш дала открытая территория,
не форум. Форум начинает работать со второго раунда, когда в нём есть чужие
`ZONE` и `NEXT`: агенты 4 и 5 прочитали три отчёта, оба не стали дублировать и
принесли находки другого класса (права на файл состояния, необработанный
`returncode` перед удалением данных).

Отсюда протокол: **раунд 1 — 2-3 агента параллельно** (дисперсию даёт не форум,
а разные стартовые вопросы, если хочешь их задать); **раунд 2+ — по одному-два,
с обязательным чтением форума**.

Промпту раунда 2+ нужны две строки, иначе агент вернёт чужое своими словами:

```
Возьми зону, которую НИКТО не брал. Повторять чужой поиск запрещено:
вернёшь находки, уже записанные в форуме, — прогон не засчитан.
SEEN: сколько чужих находок ты прочитал в форуме (числом). Подтверждать
или оспаривать их не нужно — это работа верификации, не твоя.
```

⚠️ `SEEN` — счётчик прочитанного, **не голос**. Просить агента «перепроверить и
подтвердить» чужие находки нельзя по двум причинам сразу: он прочтёт вместе с
заявлением и `WHY` автора, то есть заякорится (раздел 5 требует обратного —
верификатору дают только заявление), и получится ровно голосование, которое
разделом 5 объявлено не-верификацией.

**Одиночество находки не понижает её вес.** То, что находку не продублировал
никто, — не довод против неё: у роя один агент на зону, дублировать её просто
некому. Вес даёт только эмпирический gate. Обратное правило — «подтвердили
двое, значит серьёзнее» — это голосование через чёрный ход.

**Критерий остановки:** агент вернул пустой `FINDINGS` при ненулевом `SEEN` —
территория исчерпана, рой сошёлся. Пустой `FINDINGS` при нулевом `SEEN`
означает другое: агент не читал форум, перезапусти.

Дальше находки роя идут в ту же верификацию (раздел 5) — рой добывает
кандидатов, а не находки. `MAP` со строками «не смотрел» едет в отчёт Шага 7
как строки «пропущено».

<a id="верификация"></a>
## 5. Верификация: почему не голосование

**Голосование N агентов не работает.** Зафиксированный случай: 80+ агентов
единогласно подтвердили несуществующую уязвимость в OpenSSL — её убил один
эмпирический тест. Модели сходятся в общих приорах обучения, а не в истине;
«спросить ещё пятерых» усиливает согласие, а не точность.

Что работает:

1. **Разделение ролей.** Тот, кто нашёл, не верифицирует. Разные промпты.
2. **Context asymmetry.** Верификатору дают **только заявление** —
   «`is_safe_ip` пропускает IPv4-mapped IPv6» — и путь к файлу. Reasoning
   автора не передают: иначе верификатор заякорится и согласится.
3. **Задача сформулирована как опровержение.** «Попробуй показать, что это НЕ
   баг» ловит больше, чем «проверь, баг ли это».
4. **Эмпирический gate.** Вердикт «подтверждено» требует вывода прогона —
   импорт реальной функции проекта и вызов с атакующим входом. Без прогона
   максимум `[UNVERIFIED]` и severity ≤ MEDIUM (правило из Шага 3).

Три исхода верификации, все легитимны: подтверждено (с выводом) · снято
(гипотеза не подтвердилась) · не проверяется (почему именно, и каким тестом
это проверит пользователь).

### PoC обязан иметь контрольную группу

Мало показать, что баг воспроизводится, — покажи, что **исправленный вариант
того же PoC даёт другой результат**. Без этого ты не знаешь, что именно
воспроизвёл.

Реальный случай из прогона этого скилла: PoC двойного списания дал −20 (баг
есть), но «исправленная» версия дала те же −20. Значит объяснение причины было
неверным: списание в PoC шло безусловно, независимо от статуса hold, и правка
условия ничего не меняла. Пока контрольная группа не даёт **другой** результат,
у тебя есть воспроизведённый симптом, но не понятая причина — а чинить будут по
твоему объяснению.

Правило: PoC = уязвимый вариант (ожидаем плохой результат) + исправленный
вариант (ожидаем хороший). Совпали — ищи ошибку в самом PoC, а не в коде.

<a id="шаблоны"></a>
## 6. Шаблоны промптов

### Агент волны 1 (discovery)

```
Работай сам, НЕ создавай субагентов.

Ты ищешь уязвимости класса <ЛИНЗА> и только этого класса.

Твой срез — стартовые файлы, а не забор: <пути из инвентаря>
[если инвентарь деградировал до модулей — вместо путей подставь эту ветку:]
Твоя зона — <модуль/сервис>, путей в инвентаре для неё нет. Первым делом
сам построй поэндпоинтный список внутри зоны (точки входа, что их вызывает,
есть ли проверка прав) и верни его отдельным блоком ZONE_MAP вместе с
находками — он закрывает строку «не разворачивал» в инвентаре. За границу
зоны не выходи, кроме реализаций проверок по правилу ниже.
Если вердикт «здесь безопасно» опирается на вызов функции, определённой вне
среза (валидатор, проверка прав, санитайзер), ты ОБЯЗАН открыть её реализацию
по импорту и прочитать — на любую глубину, пока не увидишь сам код проверки.
Оценивать `validate(x)`, не открыв `validate`, запрещено: это чаще всего и
есть место бага. Всё прочее вне среза не читай — записывай в blind_spots.

Что искать: <2-4 конкретных вопроса из таблицы линз>

Верни список КАНДИДАТОВ (гипотез, не подтверждённых находок). Для каждого:
- claim: одно предложение, что именно сломано
- location: file:line
- why: почему ты думаешь, что это баг (2-3 строки)
- how_to_verify: каким прогоном это можно подтвердить

Затем отдельным списком верни blind_spots — что тебе нужно было прочитать,
но ты не смог (нет доступа, не нашёл, вне среза и не по импорту). Формат:
путь или имя модуля + одна строка, какой вопрос остался без ответа.
Пустой blind_spots допустим, но только если ты действительно дошёл до кода
всех проверок, на которые сослался.

Гипотеза о классе уязвимости, не подтверждённая чтением конкретного кода
(«такие валидаторы обычно ломаются на DNS rebinding»), — это НЕ кандидат.
Либо открой код и покажи строку, либо отправь вопрос в blind_spots.

Отсутствие находок — ПОЛНОЦЕННЫЙ ответ. Верни пустой список и напиши, что
проверял. Не придумывай находку, чтобы не вернуться с пустыми руками.

Не чини код. Не пиши отчёт для человека. Твой ответ — данные для сборки.
```

### Агент верификации (по одному на кандидата)

```
Работай сам, НЕ создавай субагентов.

ЗАЯВЛЕНИЕ: <claim>
ГДЕ: <file:line>

Твоя задача — ОПРОВЕРГНУТЬ это заявление. Оно, скорее всего, неверно:
типичные причины — код недостижим, проверка есть выше по стеку, вход
невозможен от внешнего пользователя, поведение намеренное.

Порядок:
1. Прочитай код по указанному пути и вокруг.
2. Напиши минимальный скрипт, который ИМПОРТИРУЕТ реальную функцию проекта
   и вызывает её с атакующим входом. Не переписывай логику своими словами —
   так ты проверишь свою копию, а не код проекта.
3. Запусти его.

Верни:
- verdict: confirmed | refuted | untestable
- evidence: дословный вывод прогона (для confirmed — обязательно)
- reason: почему опровергнуто / что помешало проверить
- severity: CRITICAL|HIGH|MEDIUM|LOW — но выше MEDIUM только при наличии evidence

Если проверить не удалось — verdict: untestable и что именно помешало.
"Не смог проверить" ≠ "проверить невозможно": сначала попробуй поднять
окружение или замокать зависимость.
```

<a id="лимиты"></a>
## 7. Лимиты и бюджет

- **Одновременно ≤ 8 агентов.** Платформенный потолок — 20, но на 20 растёт
  риск упереться в лимит с невосстановимой ошибкой. 8 — рабочий дефолт.
- **200 субагентов на сессию**, глубина вложенности 3. Агентам явно
  запрещено плодить своих — иначе упрёшься в глубину и потеряешь отчёты.
- **Модель по задаче:** discovery и верификация — обычная рабочая модель;
  экономить на верификации нельзя, это последняя линия против ложных находок.
  **Верификатор — на другой модели, чем нашедший.** Одинаковая модель ошибается
  в схожих местах ~60% времени: тот же приор, который породил ложного кандидата,
  склонен его же и подтвердить. Смена модели даёт дисперсию бесплатно, тогда как
  второй агент на той же модели даёт то же мнение по двойной цене.
- **Иерархию в промптах не изобретай.** Роли («ты тимлид»), назначенный
  агент-начальник, дерево подчинения — замерено, что разницы не дают вообще.
  Работает разделение вопроса (линза, зона, территория), а не разделение званий.
- **Цена правила «дойди до реализации проверки».** Замер 17.08.2026: агент,
  обязанный либо показать строку кода, либо признать `blind_spot`, поднимает
  окружение и гоняет код — 91-100k токенов и 6-9 минут против 62k и 50 секунд у
  агента, читающего только выданный срез. Втрое дороже; на десятке линз это
  разница между «за обед» и «за вечер». Правило того стоит (0/2 против 2/2 на
  реальных багах), но закладывай бюджет заранее.
- **Бюджет.** Волна 1 из 5 линз + волна 2 + верификация 6 кандидатов ≈ 12
  агентов. На большом репо с разбиением по срезам счёт идёт на десятки —
  оценивай до запуска и скажи пользователю, если счёт большой.

<a id="сборка"></a>
## 8. Сборка результатов

Дедуп кандидатов делай **плоским кодом, не агентом**: ключ «файл + строка +
класс». Два агента с разными линзами часто указывают на одно место — это не
две находки.

⚠️ Дедупь против множества **всех виденных** кандидатов, а не только
подтверждённых. Иначе снятые верификацией гипотезы всплывут снова на следующем
круге, и цикл не сойдётся.

**`ZONE_MAP` и `blind_spots` собери до отчёта, иначе инвентарь останется врать.**
Агент, работавший по границе зоны, вернул поэндпоинтный список — впиши его в
`surface.md` вместо строки «не разворачивал»; агент, упёршийся в нечитаемое, вернул
`blind_spots` — они идут в таблицу охвата Шага 7 строками «пропущено» с причиной.
Не перенёс — Шаг 7 покажет покрытие, которого не было.

В отчёт из фан-аута идёт то же, что из обычного прогона (Шаг 8), плюс:

- сколько агентов, по каким линзам, какие срезы кода покрыты;
- кандидаты, снятые верификацией — в раздел «Снятые гипотезы» с причиной;
- **что не покрыто ни одной линзой** — самая ценная строка отчёта, потому что
  фан-аут создаёт ложное ощущение полноты: агентов было много, значит
  посмотрели всё. Нет: посмотрели ровно то, что было в инвентаре.
