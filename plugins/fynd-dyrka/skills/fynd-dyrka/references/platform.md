# Безопасность прод-развёртывания (platform layer)

`iac` смотрит файлы в репозитории (Dockerfile, terraform, k8s-манифесты) —
что *задумано*. Этот файл смотрит реальное состояние прода — что *развёрнуто
и настроено сейчас*, включая ручные правки в консоли платформы, которые ни в
каком репозитории не отражены. Платформо-агностично: конкретные команды даны
для Railway/Vercel/Fly/Heroku/k8s/Docker/AWS там, где применимо.

## 1. Экспозиция сервисов

| Вопрос | Чем плохо | Как проверить |
|---|---|---|
| БД (Postgres/Mongo/MySQL) слушает публичный адрес? | Прямой доступ в обход API-уровня; брутфорс/эксплойт БД снаружи | Railway: `list_domains` / `list_tcp_proxies` на сервисе БД — есть ли внешний proxy; `private_network_status`. Fly: `fly status` — секция Services, публичные порты. AWS: `aws rds describe-db-instances --query 'DBInstances[].PubliclyAccessible'` |
| Redis/кэш публичен и без пароля? | Полный доступ к сессиям/кэшу; задокументированный путь к RCE — `CONFIG SET dir`+`dbfilename`+`SAVE`, дописывающий SSH-ключ или cron на диск (redis.io/security); `MODULE LOAD` — тоже, но требует своего `.so` на хосте | Внешний порт + `redis-cli -h <host> ping` без auth: `PONG` = пароля нет, `NOAUTH` = защищён. Пустой ответ — вероятно, отсекает protected-mode |
| Воркер/очередь слушает HTTP там, где не должен? | Лишняя атака-поверхность на компонент без auth-слоя | Список сервисов проекта → у каждого свериться, задуман ли внешний домен |
| Админка на публичном домене без доп. защиты (VPN/IP-allowlist/Basic Auth перед приложением)? | Единственный барьер — логин/пароль приложения | Проверить домены сервиса, отдельно — есть ли админ-роут на том же домене, что и публичный API |
| Метрики/Prometheus/`/metrics`, `/actuator`, `/debug/pprof` торчат наружу? | Утечка версий, топологии, иногда — токенов в labels | `curl <domain>/metrics` — код ответа и наличие данных без auth |
| Дебаг-порты (Node `--inspect`, `.NET` remote debug, Python `debugpy`, Java JMX) открыты? | Полный RCE через debug-протокол | Список открытых портов сервиса; в конфиге — флаги запуска на предмет `--inspect=0.0.0.0` |
| Managed БД имеет и приватный, и публичный endpoint одновременно? | Публичный endpoint обычно оставляют «чтобы подключаться локально» и забывают закрыть | Railway: сравнить `private_network_status` (должен использоваться для service-to-service) с `list_tcp_proxies`/`list_domains` (публичный доступ) — если оба активны, публичный не нужен почти никогда |

Классика: managed Postgres с публичным TCP proxy «чтобы Ивану было удобно
подключаться DBeaver'ом» — с боевыми данными и слабым паролем. Спрашивай
прямо: «кто-то реально подключается снаружи регулярно, или это оставили
после разового дебага?».

## 2. Переменные окружения и секреты в рантайме

| Вопрос | Чем плохо | Как проверить |
|---|---|---|
| Где хранятся секреты — платформа-native vault или plaintext в конфиге/образе? | plaintext в Dockerfile/образе = секрет уезжает в реестр навсегда | `docker history <image>` на предмет `ENV`/`ARG` с секретами; grep Dockerfile |
| Кто в команде видит значения переменных, не только их имена? | Лишний доступ = лишняя точка утечки | Права/роли в платформе (Railway teams, Vercel project members) |
| Есть дефолты-заглушки в коде (`JWT_SECRET = "changeme"`, `os.getenv("KEY", "test")`)? | Забытый дефолт в проде = бэкдор без секрета | grep кода на `getenv(..., "` с непустым вторым аргументом; сверить с реальным значением в рантайме |
| Публичные префиксы (`NEXT_PUBLIC_`, `VITE_`, `REACT_APP_`, `EXPO_PUBLIC_`) не содержат секрет по ошибке? | Переменная с таким префиксом попадает в клиентский бандл — читается кем угодно | grep по `NEXT_PUBLIC_\|VITE_\|REACT_APP_\|EXPO_PUBLIC_` в списке переменных сервиса; сверить каждую — не ключ ли это с широкими правами |
| Одни и те же секреты в dev/staging/prod? | Утечка dev-окружения (слабее защищено) компрометирует прод | Сравнить значения (не имена) между окружениями — Railway: `list_variables` на каждый environment проекта |
| Секреты ротируются, или живут с момента создания проекта? | Утёкший год назад ключ до сих пор рабочий | Дата последнего изменения переменной, если платформа её показывает; иначе спросить у пользователя |
| `.env` с реальными значениями закоммичен или лежит в артефактах CI? | Секрет в истории git = утёк навсегда | Уже покрыто слоем secrets-сканирования; здесь — доп. проверка, что рантайм-значения не совпадают с закоммиченными |

## 3. Разница dev/prod

| Вопрос | Чем плохо | Как проверить |
|---|---|---|
| Debug-режим включён в проде (`DEBUG=True`, `NODE_ENV` не `production`, Flask/Django debug)? | Подробные стектрейсы, интерактивная debug-консоль (Werkzeug) = RCE | `curl` на несуществующий роут/с битым инпутом — смотреть, возвращается ли стектрейс с путями и версиями |
| Source maps (`.map`) доступны в проде? | Деминификация всего фронтенд-кода, включая внутреннюю логику и иногда секреты | `curl <bundle>.js.map` — 200 или 404 |
| Seed-данные / тестовые аккаунты живы в проде (`admin/admin`, `test@test.com`)? | Готовый вход в обход обычной регистрации | Проверить наличие сид-скрипта, запускался ли он на prod БД; попытка логина известными тестовыми кредами (только с разрешения) |
| CORS `*` или `Access-Control-Allow-Origin` отражает Origin — осталось с разработки? | В связке с credentials — кража сессии с любого сайта (playbook 5 в `playbooks.md`) | `curl -H "Origin: https://evil.com" -I <api>` — что в ответе |
| Проверка TLS отключена в исходящих запросах (`NODE_TLS_REJECT_UNAUTHORIZED=0`, `verify=False`, `curl -k`)? | MITM на весь исходящий трафик сервиса | grep переменных окружения и кода на эти флаги |
| Логи в проде на уровне `debug`/`trace`? | Утечка PII/токенов в логи, которые кто-то читает | Уровень логирования в конфиге запуска сервиса |

## 4. Сеть и транспорт

| Вопрос | Чем плохо | Как проверить |
|---|---|---|
| HTTPS принудительный, HTTP редиректит на HTTPS? | Трафик читается/подменяется на пути | `curl -I http://<domain>` — код 30x на https, не 200 |
| HSTS выставлен (`Strict-Transport-Security`), с разумным `max-age`? | Без HSTS — downgrade-атака на первом заходе | `curl -I https://<domain>` — заголовок и `max-age` |
| Версия TLS ≥ 1.2, слабые шифры отключены? | Устаревший TLS = известные атаки (POODLE, BEAST) | `nmap --script ssl-enum-ciphers -p 443 <domain>` или `testssl.sh` |
| Внутренний трафик между сервисами (API↔БД, API↔воркер) шифруется? | В общей публичной сети — перехват в среде, где приватность не гарантирована | Railway/Fly: используется ли `private_network`/6PN, а не публичные адреса, для service-to-service |
| Сервисы одного проекта реально в приватной сети, а не просто «рядом»? | Без приватной сети внутренний вызов = внешний HTTP-запрос, который виден снаружи | Railway: `private_network_status`; Fly: `fly ips private`; k8s: NetworkPolicy есть/нет |

## 5. Доступ к данным

| Вопрос | Чем плохо | Как проверить |
|---|---|---|
| Кто может подключиться к БД — весь интернет, VPC, или только сервис-приложение? | Шире круга — больше поверхность атаки | См. раздел 1 (экспозиция) + security groups/firewall rules платформы |
| Приложение ходит в БД под суперюзером, или под отдельным пользователем с ограниченными правами? | Компрометация приложения = полный контроль над БД (DROP, доступ к другим схемам) | Строка подключения в переменных окружения — имя пользователя; права этого пользователя в БД (`\du` в psql) |
| Бэкапы вообще делаются? | Инцидент/ransomware = потеря всех данных без возможности восстановить | Настройки managed БД (Railway/RDS/Cloud SQL — automated backups on/off), расписание |
| Бэкапы шифруются в покое? | Утечка бэкапа = утечка всей БД в plaintext | Настройки шифрования storage, где лежат бэкапы (managed сервис обычно шифрует по умолчанию — проверить, не отключено ли) |
| Восстановление из бэкапа хоть раз проверялось? | Бэкап, который не восстанавливается, — это не бэкап | Спросить дату последнего restore-теста; если никогда — красный флаг |
| Кто имеет доступ к бэкапам (отдельная политика от доступа к прод-БД)? | Бэкап часто менее защищён, чем сама БД — та же ценность данных | Права на bucket/storage с бэкапами отдельно от прав на саму БД |

## 6. CI/CD и цепочка поставки

| Вопрос | Чем плохо | Как проверить |
|---|---|---|
| Секреты в GitHub Actions/GitLab CI — через encrypted secrets, или в plaintext YAML? | Секрет в YAML = утёк в историю репозитория | grep workflow-файлов на литералы вместо `${{ secrets.X }}` |
| Есть `pull_request_target` с checkout чужого форка и последующим запуском кода/использованием секретов? | Классическая инъекция: PR из форка получает доступ к секретам репозитория | grep `.github/workflows/*.yml` на `pull_request_target` + `actions/checkout` с `ref: ${{ github.event.pull_request... }}` |
| Кто может задеплоить в прод — любой мерж в main, только тег/релиз, только вручную с апрувом? | Без гейта — компрометация любого контрибьютора = деплой в прод | Правила ветки (branch protection), наличие environment-gate с required reviewers |
| Образы подписаны (cosign/Notary), проверяется подпись перед деплоем? | Подмена образа в реестре между сборкой и деплоем не детектируется | Наличие `cosign verify` в пайплайне деплоя |
| Базовые образы — из официального источника, с зафиксированной версией, а не `:latest`? | `:latest` = непредсказуемый образ на каждой сборке, риск supply-chain через апстрим | `FROM` в Dockerfile — есть ли digest/тег версии |
| Кто имеет push-доступ к реестру образов? | Лишний доступ = возможность подменить образ напрямую, в обход CI | Права на registry (Docker Hub org, GHCR, ECR) |
| Зависимости пинятся с lock-файлом, устанавливаются `--frozen`/`--ci`, а не `latest` на сборке? | Смещение версии между dev и prod-сборкой (это уже частично покрыто deps-слоем, но проверить именно рантайм CI-команду) | Команда установки в CI — `npm ci` vs `npm install`, `pip install -r` без hash-pinning |

## 7. Идентичность и доступ к самой платформе

| Вопрос | Чем плохо | Как проверить |
|---|---|---|
| MFA включён на аккаунте платформы (Railway/AWS/GitHub/Vercel)? | Пароль слили — полный доступ ко всей инфраструктуре | Настройки аккаунта/организации на платформе; спросить пользователя, если доступа нет |
| Кто в команде имеет прод-доступ — весь состав, или только нужные роли? | Больше людей с доступом = больше векторов (фишинг, слитые credentials, offboarding-хвосты) | Список членов организации/проекта и их роли |
| API-токены платформы — с ограниченным scope, с TTL, или бессрочные с полным доступом? | Бессрочный полный токен = постоянный ключ от всего, если утечёт | Список активных токенов, дата создания/последнего использования |
| Уволенные/ушедшие из команды всё ещё имеют доступ? | Классический orphaned-access | Сверить список участников с актуальным составом команды |
| SSH-доступ к хостам — по ключам с passphrase, или пароль/шаренный ключ? | Пароль/шаренный ключ = не отследить, кто зашёл, легче брутфорсить | `sshd_config` — `PasswordAuthentication`, `PermitRootLogin` |
| Deploy-ключи (GitHub deploy keys, CI service accounts) — read-only там, где не нужна запись, скоуплены на один репозиторий? | Read-write deploy key, утёкший из CI, = запись в любой репозиторий с доступом | Настройки deploy keys в GitHub/GitLab — permissions и scope |

## 8. Контейнер и рантайм

| Вопрос | Чем плохо | Как проверить |
|---|---|---|
| Процесс в контейнере запущен от root? | Побег из контейнера сразу даёт root на хосте | `docker inspect <container> --format '{{.Config.User}}'` — пусто/`0` = root; Dockerfile — есть ли `USER` |
| `privileged: true` где не критично необходимо? | Полный доступ к устройствам хоста, обход большинства изоляций | `docker inspect --format '{{.HostConfig.Privileged}}'`; k8s — `securityContext.privileged` в манифесте |
| Лишние Linux capabilities не сброшены (`--cap-drop=ALL` + точечный `--cap-add`)? | `CAP_SYS_ADMIN`/`CAP_NET_RAW` и т.п. по умолчанию расширяют поверхность побега | `docker inspect --format '{{.HostConfig.CapAdd}} {{.HostConfig.CapDrop}}'` |
| Смонтирован `/var/run/docker.sock` внутрь контейнера? | Равнозначно root на хосте — можно поднять любой контейнер с любыми правами | `docker inspect --format '{{.Mounts}}'` на предмет `docker.sock` |
| Файловая система контейнера read-only там, где нет нужды писать? | Без read-only — успешный RCE закрепляется записью в сам контейнер | `docker inspect --format '{{.HostConfig.ReadonlyRootfs}}'` |
| Заданы лимиты CPU/памяти? | Без лимитов один сервис (или один баг с утечкой памяти) кладёт весь хост и все соседние сервисы | `docker inspect --format '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}'`; k8s — `resources.limits` в манифесте; Railway/Fly — план сервиса |

## 9. Наблюдаемость и реакция

| Вопрос | Чем плохо | Как проверить |
|---|---|---|
| Значимые события логируются (auth-фейлы, смена прав, платежи, админ-действия)? | Инцидент произошёл и не оставил следа — расследовать нечем | Проверить формат логов на наличие этих событий; Railway: `get_logs` на сервисе |
| В логи не пишутся секреты/PII (пароли, токены, номера карт, полные email в plaintext)? | Логи — частая точка утечки, доступ к ним шире, чем к самой БД | grep реальных логов на паттерны токенов/email/номеров карт |
| Есть алерты на аномалии — всплеск 5xx, всплеск исходящего трафика, резкий расход квоты у внешнего API? | Инцидент/абьюз замечают только постфактум, по счёту | Railway: `http_error_rate`, `service_metrics`; наличие алертинга (Sentry/Datadog/встроенные алерты платформы) |
| Кто реально увидит алерт — есть канал (Slack/PagerDuty/email), кто-то его читает? | Алерт настроен и уходит в пустоту — эквивалент отсутствия алерта | Спросить, куда шлются алерты и когда последний раз на них реагировали |
| Ретенция логов — достаточна для расследования (обычно от 30 дней)? | Лог ротировался раньше, чем заметили инцидент | Настройки ретенции платформы/лог-агрегатора |

## 10. Отказоустойчивость конфигурации

| Вопрос | Чем плохо | Как проверить |
|---|---|---|
| Настроен healthcheck (не просто «процесс жив», а функциональная проверка)? | Платформа считает сервис здоровым, пока он отвечает 200 на `/`, хотя БД внутри недоступна | Конфиг сервиса — путь healthcheck, что именно он проверяет |
| Restart-политика задана (`always`/`on-failure` с backoff, не `no`)? | Падение процесса = простой до ручного вмешательства | `docker inspect --format '{{.HostConfig.RestartPolicy}}'`; Railway/Fly — restart policy в конфиге сервиса |
| Что происходит при недоступности зависимости (БД/внешний API) — деградация или каскадный краш? | Один упавший компонент кладёт весь сервис вместо частичной работы | Код — есть ли timeout/circuit breaker на внешние вызовы; поведение при остановленной БД (тестируется отдельно) |
| Автоскейл имеет верхний лимит? | Без потолка — DoS-атака или баг с ретраями превращается в неограниченный счёт | Railway: `get_service_config`/`environment_status` — replica limits; AWS ASG — `MaxSize` |
| Лимиты на внешние API-вызовы с billing (LLM, SMS, email-провайдер) — есть quota/rate-limit на своей стороне? | Утёкший ключ или баг в цикле = счёт на десятки тысяч за часы | Настройки провайдера — есть ли spending limit, дневная квота |

## Как получить конфиг платформы

| Платформа | Способ |
|---|---|
| Railway | MCP: `list_variables`, `get_service_config`, `list_domains`, `list_tcp_proxies`, `private_network_status`, `list_services`, `list_projects`, `environment_status`, `service_metrics`, `get_logs` |
| Vercel | `vercel env ls`, `vercel project ls`, `vercel inspect <deployment>` |
| Fly.io | `fly config show`, `fly secrets list`, `fly status`, `fly ips list`, `fly certs list` |
| Render | Dashboard API (`GET /v1/services`) или веб-консоль — CLI ограничен |
| Heroku | `heroku config`, `heroku ps`, `heroku domains`, `heroku pg:info` |
| Docker Compose / VPS | `docker inspect <container>`, `docker compose config`, `docker network inspect` |
| Kubernetes | `kubectl get pods,svc,ingress -o yaml`, `kubectl describe networkpolicy`, `kubectl get secrets` (только имена, не значения, без прав) |
| AWS | `aws ec2 describe-security-groups`, `aws rds describe-db-instances`, `aws s3api get-bucket-acl`, `aws iam list-*` |
| GCP | `gcloud compute firewall-rules list`, `gcloud sql instances describe`, `gcloud iam service-accounts list` |

Нет доступа к платформе (нет MCP, нет CLI-сессии, нет прав) — **спроси
пользователя** («дай вывод `fly secrets list`» / «зайди в Railway → Variables
и скажи, есть ли публичный proxy на БД»). Не выдумывай конфиг и не
предполагай значения по умолчанию платформы как факт.

## Красные флаги — говорить сразу, не откладывать в конец отчёта

- Managed БД или Redis с публичным адресом и слабым/дефолтным паролем.
- Секрет с широкими правами в переменной с префиксом `NEXT_PUBLIC_`/`VITE_`/`REACT_APP_`/`EXPO_PUBLIC_`.
- `pull_request_target` с checkout PR-кода из форка в workflow, имеющем доступ к секретам.
- Docker-контейнер с примонтированным `/var/run/docker.sock` и публичным входом (веб-приложение, воркер очереди).
- Debug-режим/подробные стектрейсы, отвечающие на прод-домене.
- Один и тот же секрет (особенно платёжный/JWT/API-ключ с широким scope) в dev и prod одновременно.
- Отсутствие MFA у аккаунта с прод-доступом к платформе или облаку.
- Бэкапы не делаются вовсе, либо ни разу не проверялось восстановление.
