# Каталог SSRF-байпасов

Справочник для аудита SSRF-защиты в **чужом коде** (target-е скилла): что
проверять, когда видишь функцию вида `is_safe_url` / `validate_domain` /
allowlist приватных сетей. Каждый пункт — байпас, который типовая проверка
пропускает, плюс как его подтвердить.

> ⚠️ Это список «что искать», **не эталон правильной защиты**. Он извлечён из
> реального guard'а, в котором пункт №1 (`::ffff:`) на момент извлечения был
> **не закрыт** — то есть даже сервис, где guard выглядит серьёзным, ловится
> на этом каталоге. Не считай наличие проверки приватных сетей достаточным,
> пока не прогнал по ней эти входы.

Проверять guard нужно **воспроизводящим прогоном** (правило доказательства в
SKILL.md): импортируй настоящую функцию, прогони входы ниже, покажи, что
приватный адрес проходит как «safe». Контрольная группа — тот же вход после
разворачивания в каноничную форму.

## Паттерны

1. **IPv4-mapped IPv6** — `::ffff:127.0.0.1`, `::ffff:169.254.169.254`
   `ipaddress.ip_address()` парсит это как IPv6-адрес; проверка приватных
   IPv4-диапазонов (`10/8`, `192.168/16`, `169.254/16`) его не ловит, а в
   IPv6-списке обычно только `::1/128` и `fc00::/7`.
   Фикс, который должен быть в коде: проверять `.ipv4_mapped` и разворачивать
   в IPv4 **до** проверки сети.

2. **Децимальная / октальная / hex запись IP** — `http://2130706433/`
   (= 127.0.0.1), `http://0177.0.0.1/`, `http://0x7f.0.0.1/`
   Многие HTTP-клиенты и `socket.getaddrinfo` нормализуют это в валидный IP,
   а regex/keyword-фильтр «это домен?» такую форму пропускает мимо.

3. **`0.0.0.0` и `[::]` / `::`** — не входят в RFC1918, поэтому список
   приватных сетей их часто не содержит, но на ряде ОС резолвятся в loopback /
   any-адрес и дают доступ к локальным сервисам.

4. **DNS rebinding (TOCTOU)** — домен резолвится в публичный IP на этапе
   проверки и в приватный на этапе запроса.
   Фикс, который должен быть: резолвить **один раз**, закрепить IP, ходить по
   закреплённому IP во всех последующих запросах. Признак дыры — валидация
   резолвит домен, а HTTP-клиент потом резолвит его **заново**.

5. **Редиректы (3xx) на приватный/metadata-адрес** — первичный URL публичный,
   проходит проверку, а `Location:` ведёт на `169.254.169.254`.
   Фикс: `allow_redirects=False`, либо каждый редирект заново проходит
   SSRF-проверку. Признак дыры — проверка только входного URL + клиент с
   `allow_redirects=True`.

6. **Cloud metadata endpoints** — `169.254.169.254` (AWS/GCP/Azure/DO),
   IPv6-форма IMDS `fd00:ec2::254` (AWS).
   Обычный link-local диапазон `169.254.0.0/16` ловит только IPv4-форму;
   IPv6-metadata-адрес нужен отдельным правилом.

7. **Alternate loopback forms** — `127.1`, `127.0.1`, `0`,
   `localhost.localdomain`, любой домен, резолвящийся в `127.0.0.0/8`.
   `http://0/` на части систем = `0.0.0.0`.

8. **Keyword-фильтр как «защита»** — блок-лист подстрок
   (`localhost/internal/corp/private`) обходится доменом, который резолвится в
   приватный IP, но не содержит этих слов (`db.attacker.com` → A-запись
   `10.0.0.5`). Keyword-фильтр — UX-подсказка, **не** защита; реальная защита —
   только resolve + проверка полученного IP.

## Быстрый вопрос при аудите

Guard проверяет **резолвнутый IP** или **строку хоста**? Если строку —
пункты 1-2, 7 почти наверняка проходят. Если IP, но резолвит **дважды** — пункт
4. Если IP один раз, но клиент следует редиректам — пункт 5.
