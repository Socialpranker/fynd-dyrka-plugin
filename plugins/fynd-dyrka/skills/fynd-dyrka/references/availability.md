# Доступность и исчерпание ресурсов (DoS / cost-DoS)

Отдельный слой от конфиденциальности и целостности: угроза не «украсть данные»,
а «положить сервис» или «разорить владельца», не эксплуатируя ни одной
инъекции — только штатным использованием эндпоинта в неправильном объёме.
Сканеры (semgrep/gitleaks/osv-scanner) этот класс не находят вообще: тут нет
паттерна уязвимого кода, есть отсутствие лимита. Проверяется чтением кода на
«что здесь не ограничено» и коротким замером, а не поиском сигнатур.

## 1. Rate limiting как самостоятельный чек-пункт

| Вопрос | Как проверить | Чем кончится, если ответ плохой |
|---|---|---|
| Есть ли лимит вообще | grep на middleware (`express-rate-limit`, `slowapi`, nginx `limit_req`, Cloudflare rules) на целевом роуте | неограниченный брутфорс/скрейп/спам |
| На каком уровне стоит | эдж (Cloudflare/nginx) vs приложение (middleware) vs БД (нет вообще) | эдж без app-уровня — обходится прямым IP, если он утёк |
| Ключ лимита — IP | легко обходится: прокси-пул, ротация через Tor/резидентные прокси, IPv6 /64 (миллиарды адресов на один блок) | лимит формальный |
| Ключ лимита — user_id | обходится массовой регистрацией новых аккаунтов, если сама регистрация не лимитирована | то же самое, дороже на шаг |
| Что при превышении | 429 с `Retry-After`? Тихий бан? Просто медленнее? Ничего? | «ничего» = лимита нет по факту |
| Разделены ли дорогие и дешёвые операции | один общий лимит на весь API vs отдельный на `/search`, `/export`, `/login` | дешёвый лимит «сжирается» дорогим запросом с тем же счётчиком |

**Критично отдельно проверить эндпоинты до аутентификации** — их нечем
лимитировать по `user_id`, потому что пользователя ещё нет:
регистрация, логин, `forgot-password`, `resend-code`/OTP, email-verify,
invite-accept. Если лимит здесь только по IP (или отсутствует) —
дырка для credential stuffing, OTP-брутфорса, спам-регистрации, спама
письмами/SMS на чужой адрес (см. §9).

## 2. Дорогие эндпоинты — один запрос = много CPU/памяти/времени

Признаки в коде, по которым искать:

| В коде | Пример | Эффект |
|---|---|---|
| Сортировка/агрегация в приложении, не в БД | `results.sort(...)` / `groupBy` в JS/Python над всей выборкой | O(n log n) на каждый запрос без кэша |
| Генерация изображений/PDF/видео синхронно в обработчике | `pdfkit`, `sharp.resize`, `ffmpeg` вызван внутри HTTP-хендлера | секунды CPU на один HTTP-запрос, блокирует воркер |
| Парсинг больших структур на входе | `JSON.parse`/`yaml.load`/`csv.parse` без ограничения размера | см. §4 |
| Рекурсия по пользовательским данным без ограничения глубины | обход дерева комментариев, вложенных категорий, JSON произвольной вложенности | stack overflow / экспоненциальное время |
| N+1 запросы к БД на один HTTP-запрос | цикл с `await db.query()` внутри `.map()` | 1 внешний запрос → сотни к БД, дешёвый флуд кладёт БД |
| Синхронная тяжёлая работа в обработчике вместо очереди | отправка email/SMS/webhook, ресайз, экспорт — всё в теле хендлера | один медленный внешний вызов держит воркер/поток, пул исчерпывается быстрее чем при нормальной нагрузке |

Как подтвердить: `time curl` на подозрительный эндпоинт с реалистичным
объёмом данных на **локальной копии**, не на проде. Замерить один запрос,
не флудить.

## 3. Unbounded-запросы

| Признак | Где искать | Эффект |
|---|---|---|
| `SELECT` без `LIMIT` | ORM-вызов без `.limit()`/`.take()`, сырой SQL | выгрузка всей таблицы одним запросом |
| Пагинация без верхней границы | `?limit=` читается напрямую в запрос без `min(limit, MAX)` | `?limit=999999` = №1 в другой обёртке |
| «Экспорт всех записей» / «выгрузить в CSV» | эндпоинт без постраничной отдачи, весь датасет в память | OOM на инстансе |
| GraphQL без лимита глубины/сложности | нет `graphql-depth-limit`, `graphql-cost-analysis`, `query complexity` | вложенный запрос вида `user{friends{friends{friends{...}}}}` — экспоненциальный fan-out в БД |
| Батч-эндпоинты без лимита размера батча | `POST /batch` принимает массив произвольной длины | один HTTP-запрос = N операций, N не ограничено |

Как подтвердить: прочитать код пагинации/лимита, показать, что клиентское
значение идёт в запрос без `Math.min`/`clamp`. Локально — один запрос с
большим `limit`, замерить время и объём ответа.

## 4. Размер входа

| Что проверить | Как | Эффект без защиты |
|---|---|---|
| Лимит тела запроса | `body-parser`/`express.json({limit})`, nginx `client_max_body_size`, framework default | гигабайтный JSON в память процесса |
| Лимит загружаемого файла | максимальный размер в конфиге upload-мидлвари (multer/formidable/etc) | диск/память исчерпаны одной загрузкой |
| Декомпрессионные бомбы | сервер разжимает `Content-Encoding: gzip`/`zip` без лимита итогового размера | 1 КБ на входе → гигабайты после распаковки (zip bomb, `42.zip`) |
| Очень большой / глубоко вложенный JSON | парсер вызывается без ограничения глубины (`JSON.parse` рекурсивный) | переполнение стека парсера на вложенности вида `[[[[[...]]]]]` |
| XML-бомбы (billion laughs) | XML-парсер с включёнными entity expansion, `DOCTYPE` не отключён | несколько КБ XML разворачиваются в гигабайты в памяти |
| Множество полей/файлов в multipart | нет лимита на число частей (`maxFields`, `maxFiles` в multer/busboy) | тысячи мелких полей грузят парсер |

Как подтвердить: проверить конфиг лимитов в коде (значение выставлено или
дефолт фреймворка — какой у фреймворка дефолт, часто «безлимит»). Локально —
один запрос с телом чуть выше лимита, проверить, что сервер отвечает 413, а
не падает/виснет.

## 5. ReDoS — катастрофический backtracking

Опасные паттерны в регулярном выражении:

- Вложенные квантификаторы: `(a+)+`, `(a*)*`, `(\d+)+`
- Чередование с перекрывающимися альтернативами: `(a|a)*`, `(a|ab)*`
- Квантификатор над группой, которая сама может съесть часть того же текста
  по-другому: `([a-zA-Z]+)*$`, `(.*a){x}` при большом x

Где в коде обычно живёт пользовательский ввод внутри regex:

- Валидация email/URL/телефона (самое частое место — copy-paste regex из
  Stack Overflow с вложенными квантификаторами)
- Парсинг `User-Agent` / заголовков
- Поиск/фильтрация по строке, которую вводит пользователь
- Кастомный роутинг с regex-паттернами путей

Как проверить — изолированный замер, НЕ через сервер:

```js
// Доказательство ReDoS — РОСТ времени с длиной входа, а не одно число.
// Единичный замер ничего не доказывает: 200 мс можно списать на что угодно.
const re = /^([a-zA-Z]+)*$/;          // подставь паттерн из проекта
for (const n of [20, 25, 28, 30, 32]) {
  const evil = "a".repeat(n) + "!";   // хвост, ломающий совпадение
  const t0 = process.hrtime.bigint();
  re.test(evil);
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  console.log(`n=${n}\t${ms.toFixed(1)} ms`);
  if (ms > 5000) break;               // дальше можно не ждать
}
```

Замер этого паттерна в Node (V8): `n=20 → 107 мс`, `n=25 → 350 мс`,
`n=28 → 2345 мс`, `n=30 → 10462 мс`. Удвоение времени на каждые +1-2 символа —
это и есть подтверждение; линейный рост означает, что паттерн безопасен.
Аналог на Python — тот же цикл с `time.perf_counter()` и `re.match`.

Строка-убийца — обычно N повторов символа, попадающего в квантификатор, плюс
один символ, ломающий совпадение в конце (заставляет движок перебрать все
варианты backtracking перед тем как сдаться).

Движок безопасен (линейное время, backtracking невозможен в принципе) —
**Go (`regexp`, RE2), Rust (`regex` крейт)**. Небезопасен (backtracking-based,
уязвим по конструкции) — **JavaScript (V8), Python (`re`), Java
(`java.util.regex`), PHP (PCRE)**. Наличие такого движка в стеке — не сама
уязвимость, но повышает приоритет ручной проверки каждого regex на
пользовательском вводе.

## 6. Стоимость в деньгах (cost-DoS / cost amplification)

Современный и часто упускаемый класс: атака не кладёт сервис, а выставляет
владельцу счёт. Возникает, когда пользовательский запрос дёргает **платный
внешний API**: LLM-вызов, OCR, геокодирование, отправка SMS/email,
транскодирование видео, а также платные лимиты самой инфраструктуры —
serverless-инвокации, egress-трафик, платное хранилище.

| Вопрос | Почему важен |
|---|---|
| Есть квота на пользователя (запросов/токенов/файлов в час-день)? | без неё один аккаунт = неограниченный счёт |
| Есть глобальный дневной/месячный потолок расходов на аккаунте провайдера? | последняя линия защиты, если пользовательская квота не сработала |
| Есть алерт на всплеск трат/вызовов? | без него DoS обнаруживается только по счёту в конце месяца |
| Ограничена ли длина/размер входа, идущего в платный API? | длинный промпт/большой файл на OCR — цена за вызов растёт вместе с размером, не только с количеством вызовов |
| Кэшируются ли повторяющиеся запросы к платному API? | без кэша идентичный запрос оплачивается заново каждый раз |

Расчёт для отчёта: `цена_вызова × достижимая_частота × 3600` = стоимость часа
атаки. **Обе цифры бери из реальности, а не отсюда**: цену — из прайса
провайдера, частоту — из собственного замера на локальной копии (сколько
запросов в секунду проходит с одного соединения до того, как что-то начнёт
их резать).

Схема подстановки: `$ЦЕНА × N_req_sec × 3600 = $X/час` с одного IP, кратно
больше с прокси-пулом. Именно `$X` и есть severity-обоснование — «нет квоты»
без числа не аргумент. Если замерить частоту не вышло, так и пиши
(«частота не замерена, потолок не оценён»), а не подставляй правдоподобное
число: выдуманная цифра в отчёте хуже её отсутствия.

## 7. Таймауты и каскадные отказы

| Признак | Эффект |
|---|---|
| Нет таймаута на исходящий HTTP-запрос (к БД, к внешнему API) | один зависший upstream держит воркер бесконечно, пул исчерпывается |
| Нет ограничения на число ретраев | retry-storm: упавший upstream получает кратно больше нагрузки от ретраев в момент восстановления |
| Нет circuit breaker | сервис продолжает долбить недоступный upstream вместо быстрого fail |
| Пул соединений к БД маленький/неограниченный сверху без учёта конкурентности | параллельные медленные запросы съедают весь пул, остальные запросы встают в очередь/падают по таймауту |
| Блокирующий вызов в event loop (Node/asyncio) | один синхронный тяжёлый вызов (crypto, JSON.parse гигантского объекта) морозит весь процесс, не только текущий запрос |
| Slowloris / висящие соединения | нет таймаута на чтение заголовков/тела — соединение держится открытым, исчерпывая лимит одновременных соединений |

Как проверить: grep на `timeout` в HTTP-клиенте (`axios`, `fetch`, `requests`,
`httpx` — есть ли `timeout=` явно, или используется библиотечный дефолт,
который может быть `None`/бесконечность). Проверить конфиг пула БД
(`max connections`) против реалистичной конкурентности.

## 8. Исчерпание пространства состояний

Неограниченный рост чего-либо на диске/в памяти/в БД:

- Сессии без TTL или без верхнего лимита на пользователя
- Временные файлы (загрузки, экспорты, превью), которые не удаляются после
  использования или при обрыве соединения
- Записи в БД, создаваемые **неаутентифицированными** пользователями
  (гостевые корзины, черновики, лог-события) без TTL/очистки
- Очередь фоновых задач без backpressure — принимает работу быстрее, чем
  обрабатывает, растёт неограниченно
- Кэш без политики вытеснения (unbounded `Map`/dict в памяти процесса,
  растущий на каждый уникальный запрос)
- Логи без ротации — диск заполняется, процесс падает при записи

Как проверить: найти, где создаётся ресурс без парной операции очистки/TTL;
для кэша в памяти — есть ли `maxSize`/LRU или это голый `{}`/`Map()`.

## 9. Амплификация и внешние эффекты

Эндпоинт, превращающий сервис в источник исходящего трафика на третьих лиц:

| Паттерн | Как эксплуатируется |
|---|---|
| Отправка email/SMS на произвольный адрес по запросу пользователя (уведомление, инвайт, «поделиться») | сервис как спам-релей — атакующий указывает чужой адрес, жертва получает поток писем/SMS от легитимного домена |
| Webhook-регистрация без валидации целевого URL | сервис бьёт по указанному адресу неограниченно часто (совмещается с SSRF — см. `ssrf-bypasses.md`) |
| Эндпоинт, инициирующий много исходящих запросов от одного входящего (fetch превью ссылки, батч-уведомления, fan-out на подписчиков) | один запрос атакующего = N запросов сервиса к третьей стороне — сервис становится атакующим по амплификации |
| Retry/webhook без лимита на целевой URL атакующего | сервис как DDoS-инструмент против третьего сайта, указанного атакующим |

Проверить: есть ли лимит на количество отправок email/SMS с одного аккаунта
в час; проверяется ли, что webhook URL не указывает на инфраструктуру
самого атакующего в неограниченном цикле.

## 10. Алгоритмическая сложность

| Паттерн | Эффект |
|---|---|
| Hash-collision DoS | структура данных на пользовательских ключах уязвима к специально подобранным коллизиям (актуально для старых/кастомных хеш-таблиц, не для современных Node/Python со случайным seed) |
| Дорогой хеш пароля без rate-limit на логине | bcrypt **специально** медленный: cost 12 ≈ 150-250 мс, cost 14 ≈ 630-1000 мс на CPU 2019-2021 (каждый +1 к cost удваивает работу). Это порядок величины — замеряй на своём железе, не подставляй в отчёт как факт. Без лимита логин превращается в CPU-DoS: N параллельных попыток = N потоков заняты хешированием |
| Сортировка/поиск с квадратичной сложностью на пользовательских данных | самописный алгоритм вместо стандартной библиотеки на входе контролируемого атакующим размера |

Как проверить: замерить время ответа `/login` на неверный пароль при
10-20 параллельных запросах локально — рост времени ответа непропорционально
числу запросов указывает на исчерпание CPU-ресурса хешированием.

## Как подтверждать

Правило скилла — воспроизводящий прогон обязателен для severity выше MEDIUM.
Для DoS-находок это означает **не** флуд прода. Безопасные способы подтвердить:

1. **Замер одного запроса, не флуда.** `time curl` (или `curl -w
   "%{time_total}\n"`) на дорогой эндпоинт — если один запрос уже занимает
   секунды CPU, экстраполяция на N параллельных запросов очевидна без
   реального флуда.
2. **Расчёт вместо атаки.** «1 запрос = N секунд CPU / M МБ памяти» →
   «сколько запросов в секунду нужно, чтобы съесть весь CPU/RAM инстанса» —
   арифметика, не нагрузочный тест.
3. **Локальная копия, не прод.** Если нужно увидеть эффект под нагрузкой
   (пул соединений, backpressure) — поднять сервис локально/в контейнере и
   гонять нагрузку там.
4. **ReDoS — изолированный замер регулярки** вне HTTP-стека вообще (см. §5,
   пример на JS) — движок и паттерн те же, результат переносится на прод без
   риска положить его.
5. **Rate-limit — единичная проверка обхода**, не полный брутфорс: сделать
   N+1 запросов, где N — заявленный лимит, показать, что (N+1)-й прошёл (или
   что смена IP/аккаунта сбрасывает счётчик). Не нужно тысяч запросов —
   достаточно перейти границу один раз.
6. **Cost-DoS — расчёт по цене прайс-листа провайдера**, не реальные вызовы
   на боевом ключе.

**Явно: нагрузочную атаку по проду без отдельного явного разрешения
владельца не гонять.** Разница между «показал, что 1 запрос стоит 3 сек CPU»
и «отправил 10000 запросов и уронил прод» — это разница между PoC и
инцидентом, за который отвечает аудитор.

## Severity для DoS

Ось 1 — доступность атакующему:

- Анонимно достижимо (до аутентификации) + дёшево атакующему (1 запрос,
  без спецсредств) + дорого жертве (много CPU/памяти/денег на один запрос)
  → **HIGH/CRITICAL**.
- Требует аутентификации, но регистрация свободная и сама не лимитирована
  → почти то же самое, на один шаг дороже → всё ещё **HIGH**, если эффект
  общий (не только своя сессия).
- Требует аутентификации, эффект ограничен собственной сессией/аккаунтом
  атакующего (например, забивает свою же квоту) → **LOW/MEDIUM**.

Ось 2 — асимметрия стоимости. Чем больше разрыв между «что тратит
атакующий» и «что тратит жертва», тем выше severity: 1 HTTP-запрос → минуты
CPU или доллары счёта — явный признак амплификации, не просто нагрузки.

Cost-DoS оценивать **в деньгах за час атаки** (см. формулу в §6), не в
абстрактных категориях — конкретная цифра убедительнее для приоритизации,
чем «может привести к повышенным расходам».

Понижающие факторы: эффект временный и самовосстанавливается (rate-limit
